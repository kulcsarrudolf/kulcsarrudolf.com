# My personal blog and portfolio

Source for [kulcsarrudolf.com](https://kulcsarrudolf.com): a portfolio of projects and a blog, in English and Hungarian.
The preview deployment is [kulcsarrudolf.vercel.app](https://kulcsarrudolf.vercel.app).

`master` deploys to production, `develop` to the preview URL.

## Stack

TanStack Start (TanStack Router + Vite) with Nitro building the server bundle for Vercel, TypeScript and Tailwind throughout, Storybook for the components, and oxlint in place of ESLint.
Posts are parsed with gray-matter and rendered with markdown-to-jsx.
Blog post images use [zimme-zoom](https://www.npmjs.com/package/zimme-zoom), my own click-to-zoom library.

## How it is put together

- `src/routes/` holds one file per URL.
  A route declares its `loader` (data), `head` (title, meta, canonical, JSON-LD) and `component`.
- `src/server/content.ts` reads the Markdown at build time with `import.meta.glob`, so the deployed function never touches the filesystem.
- `src/server/functions.ts` exposes that content through server functions.
  Loaders call them, which works on the server during SSR and in the browser on client-side navigation.
- `src/start.ts` registers the request middleware that answers `.md` URLs and `Accept: text/markdown` requests with plain markdown.
- `src/routes/sitemap[.]xml.ts` and `src/routes/llms[.]txt.ts` generate the sitemap and `llms.txt`.
- `src/routeTree.gen.ts` is generated by the router plugin on every dev server start or build.
  It is committed so type-checking works without a build.
- Translations live in `src/i18n/translations/` (`en.json`, `hu.json`).

Every page is rendered on the server at request time.
Nothing is prerendered, so the `?lang=` query, the markdown content negotiation and the draft preview on the dev server all keep working in production.

## Getting started

This project uses Yarn; a `preinstall` check makes npm and pnpm fail.

```bash
git clone https://github.com/kulcsarrudolf/kulcsarrudolf.com.git
yarn install
yarn dev
```

Other scripts: `yarn build` (production build into `.output/`), `yarn start` (serve the built app with Node), `yarn typecheck`, `yarn lint`, `yarn format`, `yarn deploy` (fast-forward `master` to `develop` and push).

### Storybook

`yarn storybook` runs on [http://localhost:6006](http://localhost:6006); `yarn build-storybook` writes a static build to `storybook-static/`.
Every component under `src/components/` has a story next to it (`*.stories.tsx`).

Stories render inside a real TanStack Router with an in-memory history, so `<Link>`, `useNavigate` and `useSearch` work without the app shell.
The toolbar has a language switch that sets the same `?lang=` query the site uses.
Configuration lives in `.storybook/`, on its own small Vite config, because the app's config carries the TanStack Start and Nitro plugins.

### Linting and formatting

`yarn lint` runs [oxlint](https://oxc.rs/docs/guide/usage/linter).
The rules live in `.oxlintrc.json`: correctness rules as errors, rules-of-hooks and exhaustive-deps on, unused variables allowed with a leading underscore, and `max-lines` capping every file at 500 lines.

`yarn format` runs [oxfmt](https://oxc.rs/docs/guide/usage/formatter), oxlint's formatter, over the TypeScript, JSON, CSS and Markdown in the repo; `yarn format:check` reports without writing.
It reads `.oxfmtrc.json`, which skips the generated `src/routeTree.gen.ts`, and `.gitignore`.

Neither is something to remember. `yarn install` installs a Husky pre-commit hook that runs [lint-staged](https://github.com/lint-staged/lint-staged) over the staged files, in the order [lint-staged.config.js](./lint-staged.config.js) lists them: `oxlint --fix`, then `oxfmt`, then `tsc --noEmit`.
Whatever the first two rewrite is staged along with the commit.
An unfixable lint error or a type error aborts the commit and leaves the working tree as it was.

The typecheck is the whole project rather than the staged files, because that is the only way `tsc` reads `tsconfig.json`, so a type error anywhere stops the commit even if it sits in a file the commit does not touch.
It is skipped for a commit that only touches Markdown or CSS.

`git commit --no-verify` skips the hook.

### Environment variables

Client-side variables need the `VITE_` prefix.
Put them in `.env.local` locally and in the Vercel project settings for deployments.

| Variable                    | Purpose                                         |
| --------------------------- | ----------------------------------------------- |
| `VITE_ENV`                  | Set to `production` to enable Vercel Analytics. |
| `VITE_WEB3FORMS_ACCESS_KEY` | Web3Forms access key used by the contact form.  |

## Adding a post or a project

Posts live in `src/posts/`, projects in `src/projects/`, one Markdown file each, and the file name becomes the URL: `src/projects/pg-seed-kit.md` renders at `/projects/pg-seed-kit`.
Copy the template ([post](./src/posts/tempate/template-post.md), [project](./src/projects/template/template-project.md)), fill in the frontmatter, and write the body.

`private: true` keeps a post or project on the local dev server only.
Projects also take `order` (position on `/projects`, ascending, default `100`), the optional `github`, `npm` and `website` links, and `relatedPosts` as a list of blog post slugs. Private posts are filtered out of that list, so referencing a draft is safe.

## Markdown for AI agents

Every post and project page is also served as clean markdown, so agents can read the content without parsing HTML.
Append `.md` to the URL (`https://kulcsarrudolf.com/projects/pg-seed-kit.md`), or request the normal URL with an `Accept: text/markdown` header.
`/llms.txt` lists every post and project with a summary and a link to its markdown version.
